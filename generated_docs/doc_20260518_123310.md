# Product Catalog Service Documentation

## 1. Overview

The `ProductCatalog` service is a core component within a modern e-commerce or retail application architecture. Its primary responsibility is to store, manage, and retrieve comprehensive information about all products offered. It acts as the single source of truth for product data, enabling other services (like storefronts, search, inventory, recommendations, etc.) to access up-to-date and consistent product details.

### 1.1. Purpose

The main purposes of the `ProductCatalog` service include:
*   **Centralized Product Data Management**: Provides a unified repository for all product-related information.
*   **Data Consistency**: Ensures that all consuming services access the same, accurate product data.
*   **Decoupling**: Separates product data concerns from other business domains (e.g., orders, inventory, payments).
*   **Scalability**: Allows product data management to scale independently of other services.
*   **Rich Product Representation**: Supports complex product structures, attributes, variants, and relationships.

### 1.2. Key Responsibilities

*   **Product Information Storage**: Persisting detailed product data (name, description, price, images, specifications, etc.).
*   **Product Search & Retrieval**: Enabling efficient lookup of products by ID, SKU, name, or other attributes.
*   **Category Management**: Organizing products into hierarchical categories and subcategories.
*   **Variant Management**: Handling different product options (e.g., size, color) and their unique SKUs.
*   **Attribute Management**: Storing custom product attributes (e.g., material, brand, weight).
*   **Price Management**: Storing base pricing information for products (dynamic pricing, promotions, and user-specific pricing typically handled by a separate pricing service or logic).
*   **Product Availability Status**: Managing whether a product is "active," "discontinued," "coming soon," etc. (real-time inventory levels are usually managed by an `Inventory` service).

## 2. Architecture and Components

The `ProductCatalog` service typically follows a standard microservice pattern, encompassing a dedicated data store and a set of internal modules to handle its core functionalities.

### 2.1. Internal Modules

*   **API Layer**: Handles incoming API requests, authenticates, authorizes, and validates input.
*   **Business Logic Layer**: Contains the core logic for managing products, categories, and attributes. This includes validation rules, data transformations, and orchestrating interactions with the data access layer.
*   **Data Access Layer (DAL)**: Responsible for interacting with the persistent data store. It abstracts database-specific operations, providing a consistent interface to the business logic.
*   **Event Publisher**: Publishes events to a message broker (e.g., "ProductCreated," "ProductUpdated," "ProductDeleted") to notify other interested services.
*   **Caching Layer**: Improves read performance by caching frequently accessed product data.

### 2.2. Data Store

A relational database (e.g., PostgreSQL, MySQL) or a document database (e.g., MongoDB, DynamoDB) is commonly used. The choice depends on the complexity of the product data model and required query patterns.

*   **Relational Database (e.g., PostgreSQL)**:
    *   **Pros**: Excellent for complex relationships (products, categories, attributes, variants), strong data consistency, good for structured queries.
    *   **Cons**: Can become complex with highly nested or flexible attribute schemas, scaling read/write operations might require sharding.
*   **Document Database (e.g., MongoDB)**:
    *   **Pros**: Flexible schema, good for storing rich, semi-structured product data (e.g., dynamic attributes), scales horizontally well for reads.
    *   **Cons**: Joins between collections are less performant or require application-level handling, ensuring strong consistency across related documents can be challenging.

### 2.3. Conceptual Data Model

A simplified conceptual data model would include:

*   **Product**:
    *   `id` (UUID/Long)
    *   `name` (String)
    *   `description` (Text)
    *   `slug` (String, URL-friendly identifier)
    *   `brand` (String)
    *   `basePrice` (Decimal)
    *   `currency` (String)
    *   `imageUrl` (String, link to primary image)
    *   `status` (Enum: `ACTIVE`, `INACTIVE`, `DRAFT`, `ARCHIVED`)
    *   `categoryId` (UUID/Long, foreign key to Category)
    *   `attributes` (JSONB/Map, for flexible key-value attributes)
    *   `createdAt`, `updatedAt` (Timestamps)
*   **Category**:
    *   `id` (UUID/Long)
    *   `name` (String)
    *   `description` (Text)
    *   `slug` (String)
    *   `parentId` (UUID/Long, for hierarchical categories, nullable)
    *   `level` (Integer, for hierarchy depth)
*   **ProductVariant**: (If product has multiple options like size, color)
    *   `id` (UUID/Long)
    *   `productId` (UUID/Long, foreign key to Product)
    *   `sku` (String, unique Stock Keeping Unit)
    *   `options` (JSONB/Map, e.g., `{ "color": "red", "size": "M" }`)
    *   `additionalPrice` (Decimal, differential from baseProductPrice)
    *   `imageUrl` (String, variant-specific image)
    *   `barcode` (String)
*   **ProductImage**:
    *   `id` (UUID/Long)
    *   `productId` (UUID/Long) or `productVariantId` (UUID/Long)
    *   `url` (String)
    *   `altText` (String)
    *   `sortOrder` (Integer)

## 4. Dependencies / Integrations

The `ProductCatalog` service interacts with and depends on several other services and infrastructure components to function effectively.

### 4.1. Internal Dependencies

*   **Authentication & Authorization Service**: For securing API endpoints and ensuring only authorized users/services can modify product data.
*   **Image Storage Service (e.g., S3, Google Cloud Storage)**: While the `ProductCatalog` stores image URLs, the actual image files are hosted and managed by a dedicated storage solution.
*   **Search Service (e.g., Elasticsearch, Algolia)**: The `ProductCatalog` typically pushes product data to a dedicated search service for full-text search capabilities, faceting, and advanced filtering that are optimized for user-facing search queries.
*   **Inventory Service**: To provide real-time stock levels. While `ProductCatalog` may store a `status` (e.g., `ACTIVE`), the actual quantity on hand is managed by `Inventory`.
*   **Pricing Service**: For complex pricing rules, promotions, and user-specific pricing. The `ProductCatalog` stores the base price, but the final display price might come from a `Pricing` service.
*   **Content Management System (CMS)**: Potentially integrated for managing rich content like detailed product descriptions, marketing copy, or product guides.

### 4.2. Infrastructure Dependencies

*   **Database**: PostgreSQL, MongoDB, or similar for persistent storage.
*   **Cache (e.g., Redis, Memcached)**: For caching frequently accessed product data to reduce database load and improve response times.
*   **Message Broker (e.g., Kafka, RabbitMQ)**: For publishing events and enabling asynchronous communication with other services.
*   **Monitoring & Logging**: Tools like Prometheus, Grafana, ELK Stack for operational visibility.

## 5. Example / Usage

Consider a scenario where a `Frontend Storefront` service needs to display a product page and an `Admin Panel` needs to manage products.

### 5.1. `Frontend Storefront` - Fetching Product Details

1.  **Request**: User navigates to a product page for a product with `productId: "p123"`.
2.  **`Frontend Storefront` Action**: Makes an API call to the `ProductCatalog` service.
    ```http
    GET /product-catalog/v1/products/p123
    Accept: application/json
    ```
3.  **`ProductCatalog` Response**:
    ```json
    {
      "id": "p123",
      "name": "Super Comfy Hoodie",
      "description": "Our softest hoodie yet...",
      "basePrice": 49.99,
      "currency": "USD",
      "imageUrl": "https://cdn.yourdomain.com/images/hoodie-main.jpg",
      "category": { "id": "c456", "name": "Apparel" },
      "variants": [
        { "id": "v789", "sku": "HOD-RED-M", "options": {"color": "Red", "size": "M"}, "additionalPrice": 0.0 },
        { "id": "v790", "sku": "HOD-BLUE-L", "options": {"color": "Blue", "size": "L"}, "additionalPrice": 2.00 }
      ],
      "attributes": {
        "material": "Cotton Blend",
        "washCare": "Machine Wash Cold"
      },
      "status": "ACTIVE"
    }
    ```
4.  **`Frontend Storefront` Action (Optional)**: If inventory is critical, it might then call the `Inventory` service with the `SKUs` from the variants to get real-time stock levels.
    ```http
    GET /inventory/v1/stock?skus=HOD-RED-M,HOD-BLUE-L
    ```
5.  **`Frontend Storefront` Renders**: Combines product details and stock information to display the product page.

2.  **`Admin Panel` Action**: Makes an API call to the `ProductCatalog` service.

6.  **`Recommendation Service` Action**: Subscribes to `product.created` events, potentially updating its model or data cache.

## 6. Recommendations

### 6.1. Design Principles

*   **API First**: Design APIs carefully with clear contracts, versioning, and good documentation (e.g., OpenAPI/Swagger).
*   **Bounded Context**: Maintain clear boundaries of responsibility. `ProductCatalog` manages product *information*, not real-time inventory, pricing rules, or order history.
*   **Idempotency**: Ensure `PUT` and `DELETE` operations are idempotent. For `POST`, consider generating client-side UUIDs or returning appropriate `409 Conflict` for duplicate creations.
*   **Event-Driven Communication**: Use a message broker for cross-service communication to enhance decoupling and scalability. Avoid direct synchronous calls between services unless absolutely necessary.
*   **Caching Strategy**: Implement a robust caching strategy (e.g., Redis) for frequently accessed read operations (e.g., popular products, categories) to reduce database load.
