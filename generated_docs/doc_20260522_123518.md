# Product Catalog Service Documentation

## 1. Overview

The **Product Catalog Service (PCS)** is a core microservice responsible for centralizing, managing, and delivering all product-related information. It acts as the single source of truth for product data across an entire ecosystem, ranging from e-commerce storefronts to internal operational systems. Its primary objective is to provide a consistent, accurate, and readily available repository of product details.

**Key Responsibilities:**

*   **Product Information Management:** Store and manage comprehensive details about products, including basic information (SKU, name, description), technical specifications, marketing content, and lifecycle status.
*   **Category & Classification:** Organize products into hierarchical categories and apply various classification schemes to facilitate browsing and filtering.
*   **Attribute Management:** Define, store, and manage product attributes (e.g., size, color, material, brand) and their values, enabling rich product descriptions and filtering capabilities.
*   **Image & Asset Referencing:** Store references to product images, videos, and other digital assets (the assets themselves are typically stored in a separate asset management service).
*   **Versioning & History:** Potentially manage versions of product data or provide an audit trail of changes.
*   **Search & Discovery Enablement:** Provide product data in a format suitable for indexing by search engines, facilitating product discovery.

**Why a Dedicated Product Catalog Service?**

*   **Single Source of Truth:** Ensures consistency of product data across all consuming systems.
*   **Decoupling:** Separates product data management from other domain concerns like inventory, pricing, or orders, allowing independent development and scaling.
*   **Scalability:** Can be independently scaled to handle high read loads from various clients.
*   **Flexibility:** Enables rich and dynamic product attribute modeling without impacting core business logic elsewhere.
*   **Performance:** Optimized for fast retrieval of product information.

## 2. Components or Modules

The Product Catalog Service typically comprises several logical components or modules, each responsible for a specific aspect of product data management.

*   **Product Core Module:**
    *   Manages the fundamental product entity (SKU, Name, Description, Status, Manufacturer, Brand).
    *   Handles product lifecycle (active, inactive, retired).
    *   Manages product relationships (e.g., related products, bundles, variants).
*   **Category & Taxonomy Module:**
    *   Manages the hierarchical structure of product categories.
    *   Handles category metadata (name, description, images).
    *   Facilitates product-to-category assignments.
*   **Attribute Management Module:**
    *   Defines attribute sets and individual attributes (e.g., "Color", "Size", "Weight").
    *   Manages attribute types (text, number, boolean, dropdown, multi-select).
    *   Stores attribute values specific to each product.
*   **Asset Reference Module:**
    *   Stores URLs or identifiers for images, videos, and documents associated with products.
    *   Does *not* store the binary asset data itself.
*   **Data Persistence Layer:**
    *   Handles storage and retrieval of all product data. Typically a relational database (e.g., PostgreSQL, MySQL) for structured data or a NoSQL database (e.g., MongoDB, Cassandra) for flexible attribute schemas.
*   **API Gateway Integration (Implicit):**
    *   While not a component *of* the service, it interacts heavily with an API Gateway for external access, authentication, and routing.

## 3. APIs or Interfaces

The Product Catalog Service exposes well-defined interfaces for interaction by other services and applications.

### 3.1. RESTful API (Primary Interface)

Provides synchronous access to product data for retrieval and modification.

*   **Base URL Example:** `https://api.example.com/catalog/v1`

| Endpoint                        | Method | Description                                                   | Request Body (Example)             | Response Body (Example)                    |
| :------------------------------ | :----- | :------------------------------------------------------------ | :--------------------------------- | :----------------------------------------- |
| `/products`                     | `GET`  | Retrieve a list of products (with optional filters/pagination). | (None)                             | `[ { "id": "P123", "name": "...", ... } ]` |
| `/products/{id}`                | `GET`  | Retrieve details for a specific product.                      | (None)                             | `{ "id": "P123", "name": "...", ... }`    |
| `/products`                     | `POST` | Create a new product.                                         | `{ "name": "New Product", ... }`   | `{ "id": "P456", "name": "...", ... }`    |
| `/products/{id}`                | `PUT`  | Update an existing product.                                   | `{ "name": "Updated Name", ... }`  | `{ "id": "P123", "name": "Updated Name", ... }` |
| `/products/{id}/status`         | `PATCH`| Update partial product status (e.g., activate/deactivate).    | `{ "status": "active" }`           | `{ "id": "P123", "status": "active" }` |
| `/products/{id}`                | `DELETE`| Delete a product (soft delete recommended).                   | (None)                             | `(204 No Content)`                         |
| `/categories`                   | `GET`  | Retrieve the product category hierarchy.                      | (None)                             | `[ { "id": "C1", "name": "Electronics", "children": [...] } ]` |
| `/categories/{id}/products`     | `GET`  | Retrieve products within a specific category.                 | (None)                             | `[ { "id": "P789", "name": "...", ... } ]` |
| `/attributes`                   | `GET`  | Retrieve available product attributes.                        | (None)                             | `[ { "id": "A1", "name": "Color", "type": "dropdown" } ]` |

### 3.2. Event-Driven Interface (Asynchronous Communication)

The PCS publishes events to a message broker (e.g., Kafka, RabbitMQ) to notify other services about significant changes in product data. This ensures eventual consistency and loose coupling.

**Key Events:**

*   `ProductCreated`: Published when a new product is added to the catalog.
*   `ProductUpdated`: Published when an existing product's details change. This can be granular (e.g., `ProductPriceUpdated` if pricing is managed here, or `ProductStatusChanged`).
*   `ProductDeleted`: Published when a product is removed (or soft-deleted).
*   `CategoryUpdated`: Published when a category structure or details change.

**Message Format Example (JSON):**

```json
{
  "eventId": "a1b2c3d4-e5f6-7890-1234-567890abcdef",
  "eventType": "ProductUpdated",
  "timestamp": "2023-10-27T10:30:00Z",
  "sourceService": "ProductCatalogService",
  "data": {
    "productId": "P12345",
    "sku": "ITEM-XYZ-001",
    "name": "Super Widget Pro",
    "description": "The latest and greatest widget...",
    "categoryIds": ["CAT-ELEC-01"],
    "attributes": {
      "color": "Blue",
      "material": "Aluminium"
    },
    "status": "active",
    "version": 2
    // ... potentially include only changed fields or full product object
  }
}
```

## 4. Dependencies / Integrations

The Product Catalog Service is rarely an isolated entity. It integrates with various other systems and services across the enterprise.

### 4.1. Upstream (Data Sources / Producers)

These services provide or initiate changes to product data.

*   **Product Information Management (PIM) System:**
    *   **Integration Type:** Often the primary source for rich product data. PCS may consume data via APIs or batch imports from the PIM.
    *   **Purpose:** Ingest comprehensive product descriptions, marketing content, technical specs, and attribute definitions.
*   **Enterprise Resource Planning (ERP) System:**
    *   **Integration Type:** May provide basic product data (SKU, initial cost, basic descriptions), particularly for new product introductions or stock-keeping units.
    *   **Purpose:** Initial product setup and potentially critical identifiers.
*   **Supplier Portals/Systems:**
    *   **Integration Type:** For direct integration with third-party suppliers, receiving product data feeds.
    *   **Purpose:** Automate product data updates from external sources.

### 4.2. Downstream (Consumers)

These services consume product data from the PCS to perform their functions.

*   **E-commerce Storefront/Frontend Applications:**
    *   **Integration Type:** Primarily consumes data via RESTful API (GET requests).
    *   **Purpose:** Display product details, categories, images, specifications, and enable browsing.
*   **Search Service:**
    *   **Integration Type:** Subscribes to `ProductCreated`/`Updated`/`Deleted` events to maintain an up-to-date search index. May also pull data via REST API for initial indexing or re-indexing.
    *   **Purpose:** Enable fast, relevant product searches and filtering.
*   **Inventory Service:**
    *   **Integration Type:** May call PCS to validate product existence or retrieve basic product dimensions/weight for shipping calculations. PCS does *not* manage inventory levels.
    *   **Purpose:** Ensure inventory operations are linked to valid products.
*   **Pricing Service:**
    *   **Integration Type:** Retrieves product IDs and potentially attributes from PCS to apply pricing rules. PCS does *not* manage product prices directly.
    *   **Purpose:** Calculate and display accurate product prices.
*   **Recommendation Service:**
    *   **Integration Type:** Consumes `ProductCreated`/`Updated` events and pulls product details via REST API.
    *   **Purpose:** Generate product recommendations based on product attributes and user behavior.
*   **Order Service:**
    *   **Integration Type:** Verifies product existence and retrieves basic immutable product details (e.g., SKU, name at the time of order) via REST API when an order is placed.
    *   **Purpose:** Associate orders with specific product catalog entries.
*   **Marketing & Analytics Service:**
    *   **Integration Type:** Subscribes to product events or pulls product data for reporting, campaign segmentation, and analysis.
    *   **Purpose:** Drive marketing efforts and gain insights into product performance.
*   **Content Management System (CMS):**
    *   **Integration Type:** May pull product details to associate with rich editorial content or landing pages.
    *   **Purpose:** Enrich product presentation with marketing content.
*   **Image/Asset Management Service:**
    *   **Integration Type:** The PCS stores *references* (URLs, IDs) to assets managed by this service. The CMS or Frontend then uses these references to retrieve the actual assets.
    *   **Purpose:** Centralized storage and delivery of product media.

### 4.3. Infrastructure Dependencies

*   **Database:** (e.g., PostgreSQL, MySQL, MongoDB) for persistent storage of product data.
*   **Message Broker:** (e.g., Kafka, RabbitMQ) for asynchronous event publishing.
*   **Cache:** (e.g., Redis, Memcached) to improve read performance for frequently accessed product data.
*   **Object Storage:** (e.g., AWS S3, Google Cloud Storage) for storing the actual product assets, with PCS storing references.

## 5. Example / Usage

Consider an e-commerce storefront displaying a product page for a "Smartphone X".

1.  **User Request:** A user navigates to `/products/smartphone-x` on the storefront.
2.  **Storefront (Frontend) Action:** The storefront application makes an API call to the Product Catalog Service:
    ```http
    GET /catalog/v1/products/smartphone-x
    Accept: application/json
    ```
3.  **Product Catalog Service Response:** The PCS retrieves the product data from its database (potentially serving from cache) and returns a comprehensive JSON object:
    ```json
    {
      "productId": "smartphone-x",
      "sku": "SMART-X-64GB-BLK",
      "name": "Smartphone X (64GB, Black)",
      "description": "The latest flagship smartphone with advanced features...",
      "shortDescription": "High-performance smartphone.",
      "status": "active",
      "brand": "TechCorp",
      "categoryIds": ["electronics", "mobile-phones"],
      "attributes": {
        "color": "Black",
        "storage": "64GB",
        "screen_size_inches": 6.1,
        "camera_mp": 48,
        "os": "Android 14"
      },
      "imageUrls": [
        "https://assets.example.com/images/smartphone-x-front.jpg",
        "https://assets.example.com/images/smartphone-x-back.jpg"
      ],
      "relatedProductIds": ["case-smartphone-x", "charger-usb-c"],
      "lastUpdated": "2023-10-27T10:00:00Z"
    }
    ```
4.  **Storefront Integration:**
    *   The storefront renders the product name, description, and attributes.
    *   It uses `imageUrls` to fetch actual images from the Asset Management Service (or directly from CDN).
    *   It might use `relatedProductIds` to make further calls to the PCS or Recommendation Service to display related products.
    *   It will make a separate call to the **Pricing Service** (e.g., `GET /pricing/v1/products/smartphone-x`) and the **Inventory Service** (e.g., `GET /inventory/v1/products/SMART-X-64GB-BLK`) to get the current price and stock availability.
5.  **Product Update Scenario:** If a marketing team updates the product description via a PIM system, the PIM pushes this change to the Product Catalog Service (e.g., via its API). The PCS then updates its internal data and publishes a `ProductUpdated` event. The Search Service consumes this event, re-indexes the product, and ensures future searches reflect the new description.

## 6. Recommendations

*   **Immutable Product ID/SKU:** Design product identifiers (SKUs, internal IDs) to be immutable once created. This prevents complex cascading updates in dependent systems.
*   **Version Control for Data:** Consider implementing data versioning for product attributes or the entire product object to support historical queries or rollbacks.
*   **Caching Strategy:** Implement robust caching (e.g., Redis) for frequently accessed product details, especially for read-heavy APIs, to reduce database load and improve response times.
*   **API Design Consistency:** Maintain consistent API conventions (REST principles, naming, error handling) for ease of integration.
*   **Schema Flexibility:** For dynamic product attributes, consider a flexible schema approach (e.g., JSONB in PostgreSQL or a NoSQL database) rather than a rigid relational schema with many sparse columns.
*   **Event-Driven Architecture:** Prioritize event publishing for data changes to promote loose coupling and enable real-time reactions from other services.
*   **Security:** Implement robust authentication and authorization for API endpoints, especially for write operations (e.g., OAuth2, API Keys).
*   **Observability:** Integrate comprehensive logging, metrics (request rates, error rates, latency), and tracing to monitor service health and troubleshoot issues.
*   **Scalability:** Design for horizontal scalability, allowing multiple instances of the service to run behind a load balancer.
*   **Data Validation:** Ensure strong data validation on all incoming data to maintain data quality and integrity within the catalog.
*   **Separation of Concerns:** Strictly enforce that the PCS is *not* responsible for pricing, inventory levels, order processing, or user-specific data. It's purely about product information.
